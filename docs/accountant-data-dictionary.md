## Implemented calculations and status rules

Canonical Shopify sale amount is `original_total_presentment` from Shopify `totalPriceSet`; tax is `original_tax_presentment` from `totalTaxSet`; tax-exclusive component is total minus tax. `original_*` names denote the persisted queried money sets, not an independently frozen pre-edit invoice. Discounts are already reflected according to source totals; do not subtract `original_discounts_presentment` again. Shipping comes from `totalShippingPriceSet` and is not subtracted by canonical finance. The aggregate's “gross” means its stored tax-inclusive amount, not guaranteed pre-discount merchandise gross.

One positive, uncancelled native order qualifies if **any** JSON transaction is `status='SUCCESS'` and `kind IN ('SALE','CAPTURE')`, and its location row is not Matrixify. The query uses EXISTS: multiple successful payments do not create multiple sale rows. It counts the order total, not sum of captured money. Partial receipts may therefore differ from sale totals. Canonical finance does not require `order_customers` or `paid` financial status. Draft/custom orders can qualify through the same money evidence; they are not globally excluded.

Refunds qualify independently with a positive persisted refund total, non-null `refund_created_at`, successful refund flag and non-Matrixify app. They do not inherit the sale cancellation predicate. Amount is `-ABS(refund_total_presentment)`; tax is `-ABS(COALESCE(refund_tax_presentment,0))`; ex-tax is `-ABS(refund_total_presentment-COALESCE(refund_tax_presentment,0))`. The implementation **does** replace absent refund tax with zero; disclose this instead of calling all canonical tax complete. The collector sums refund line/shipping/adjustment tax and successful REFUND transaction amounts separately; refund total uses `totalRefundedSet`, not that transaction sum. Missing money sets become zero in collector transforms, so a stored zero is not always proof of a provider-reported zero.

Legacy non-Shopify canonical rows preserve ledger signed `gross`, `tax`, `net_ex_tax`, source/channel/currency and transaction date. They exclude every source label containing `shopify` case-insensitively. Canonical output has no store dimension separate from `source`; retain exact legacy source labels. Native Shopify is only labelled `Shopify`; shop identity is implicit in this single-shop dataset. No multi-shop crosswalk is implemented. Canonical COUNT(*) is row count; refund_events is COUNTIF, not DISTINCT refund ID; duplicates would inflate it. Legacy order_id and transaction_id are deliberately null in the CTE, so its distinct refunded-order count covers Shopify only.

The operational platform comparison applies Woo completed/processing and Shopify paid/partially_paid/partially_refunded, no cancellation, financial/location/customer presence, null retail location, non-Matrixify. It subtracts cumulative order refunds in the **order creation cohort**. Refunded status is excluded there; do not reuse that rule for canonical occurrence refunds. A present guest customer row is distinct from missing customer evidence.

Canonical Online is null retail location, POS is non-null location. Platform diagnostics separately normalise order_source into Online Store, Shop, Draft Orders, Facebook/Instagram, POS, Other identified and Unknown. Null retail location can include draft/other channels; canonical channel and an authoritative Online Store report cannot silently reconcile as the same population. Ledger source-recorded location is independent of channel and is never assigned from inventory configuration.

Amounts in Shopify and Woo API/Metorik NUMERIC money sets are source decimal currency amounts (major units); native currencies remain separate. Square raw/semantic amounts are unscaled casts/JSON amounts, with source units unverified; native Square money.amount is generally minor units. No universal division or FX is implemented by the Square semantic builder. Neither shop-vs-presentment pairs nor store names supply an accepted accounting FX rate.

`accountant_export.py` notes claim Square VAT derivation and gift-card adjustments, but contains **no implementing view DDL**. The annual-location documentation reports material Square stored component defects and explicitly preserves recorded tax. These conflicting notes are not a verified accounting policy. Obtain deployed view DDL and source reports before accepting any derived VAT, gift-card issuance exemption or component explanation. Shopify gift-card line flags exist but canonical finance applies no separate issuance/redemption exclusion. Woo gift-card history is described as incomplete. No verified fee, payout or gift-card balance table was established.

## Migration, dates and collection

November 2025 spans migration; repository documentation records public Shopify launch on **20 November 2025**, while retaining pre-launch native evidence for investigation. No canonical launch cutoff deletes 18 November or other earlier Shopify rows. Matrixify app `gid://shopify/App/1758145` is excluded from native Shopify measures; legacy Shopify labels are excluded entirely from canonical CTE. Legitimate Woo trailing refunds and residual Square Wedding/Gold/legacy activity remain. Same-day Woo/Shopify activity proves neither duplication nor independence. No accepted Woo-to-Shopify business-wide online reconciliation mapping exists in the current report contract; combined online comparisons are withheld even within one currency. Do not add a new date/status/source exclusion.

Shopify and Square builder `DATE(TIMESTAMP)` use UTC by GoogleSQL default. Woo UK API dates use GMT fields converted to UTC. Metorik stored TIMESTAMP interpretation depends on provider conversion and must be confirmed; consumers' DATE conversions use UTC. Ledger DATE already encodes an unknown upstream timezone. Europe/London is the reader's timezone, not a verified warehouse reporting timezone. A local tax period requires explicit accountant agreement and source definition review; changing timezone changes boundaries.

The bounded Shopify collector replaces selected order identities plus all their refunds atomically across locations/financials/refunds, keyed by an **updated_at half-open UTC window**, then advances successful state. It does not refresh lines/customers, whose timestamps may differ. The legacy full `/sync-shopify` path sequentially replaces tables; partial refresh is possible. Both paths exist; current operational schedule and deployed collector are unverified. Never invoke either here. Earlier annual-location docs/diagnostic still describe absence of a bounded collector; `docs/shopify-finance-refresh.md` and current code supersede that implementation statement, not their historical coverage observations.

Repository incident bounds (Shopify 24 September 2026, Square 6 September, Woo UK 9 January 2026, Woo US 19 November 2025) are prior observations, **not live findings of this handover**. Native date maxima, collection `synced_at`, successful update watermark, metadata modification and query execution time are separate. Exact Woo/Square operational end dates remain unconfirmed. Revisions/snapshots are replacements, not new sales; run attempts never count as transactions.

## Safe joins and cardinality

- Shopify financials ↔ locations/customers: intended 1:1 on order_id within the configured shop. First check each table has one row/key. Canonical CTE directly joins without ROW_NUMBER and therefore **does not deduplicate** revisions.
- Shopify lines/refunds → financials: N:1 on order_id; lines and refunds joined together become N:M. Aggregate each child independently to order/currency, then join to unique parents; never SUM repeated order totals. Payment JSON UNNEST is another child; use EXISTS for eligibility or aggregate transactions separately by ID/kind/status/currency.
- Metorik lines → orders: N:1 on `(source_store,order_id)`. WW and USD numeric IDs collide; retain platform/store on every union and join. Display numbers/names are lookup attributes, not primary keys.
- `oracle/platform-sales.js` deduplicates Shopify financials/locations with ROW_NUMBER by order_id ordered updated_at DESC, synced_at DESC; customer rows by synced_at DESC. Woo dedup is store/order_id ordered order_date DESC, full record JSON DESC. Tied conflicting Shopify revisions have no extra deterministic tiebreaker there; Woo's lexical rule is not proof of newest source update. These operational rules do not authorise changing canonical accounting dedup.
- Square order → location: N:1 by raw location_id; metadata chooses one row via JSON ordering. Lines → orders N:1 by order_id if raw orders unique; returns relate via source_order_id/source_line_item_uid, not automatically containing order. Payments' nullable order_id is never repaired; count unmatched links separately. Semantic order views do not remove raw revisions.
- Direct Woo refunds → unique API order: N:1 only after store/order uniqueness checks. Coupler orders are line-flattened; preaggregate distinct order identity before any refund join. The export's “deduplicated Woo refunds” note has no implementing rule here; obtain finance DDL rather than choose newest refund arbitrarily.
- Ledger/native joins, migrated cross-system joins and Square-to-ledger joins: no accepted universal key crosswalk established. Do not join by equal numeric ID, name, amount or date. Do not union snapshots, accountant summaries, canonical Shopify and legacy Shopify ledger as independent transactions.
