# Campaign-relative attribution continuity

The reported two-turn exchange lost campaign identity before date resolution. `analysis-context.js` previously classified “last Klaviyo campaign” as an undifferentiated campaign report and required calendar dates. A send-relative reply did not supply calendar dates, so the shared dispatcher asked the same question. Dates retained from an earlier product/conversion conversation could also silently supply an unrelated reporting range.

Campaign requests now carry a validated `campaign_request` in shared analytical context: selector, selected identity, identifiable candidates, requested attribution measures, relative date basis, user-supplied send date, clarification status, and submission cutoff. Initial campaign requests reset incompatible product/export/conversion scope. Date and candidate replies update that pending request. Explicit dates replace an earlier send-relative basis. This state survives serialization, interactive delivery and durable job result/poll recovery. Recovery commits campaign state only when the current pending campaign still matches the submitted request, preventing an older result from replacing a later clarification.

The production dependency factory supplies a read-only `resolveCampaigns({name, channel, cutoff})` provider contract. It reads governed persisted `klaviyo.entity_metadata` and collected `window_coverage`. Current governed storage represents the reviewed `production` account and email-only campaign collection; it does not claim SMS or additional-account coverage. The shared resolver nevertheless disambiguates accounts/channels when a provider supplies those populations. It picks the newest verified send within each population, retains ties, and offers names, IDs, accounts, channels, timestamps and timezones when selection is ambiguous. Exact duplicate names do not implicitly select the first candidate. Drafts, scheduled-but-unsent campaigns, flows and future sends cannot qualify. A bounded incomplete listing cannot establish an unambiguous latest campaign.

Only `actual campaign send timestamp` semantics qualify for send-relative resolution. Metadata normalization no longer substitutes `scheduled_at` or `updated` for an actual send, nor treats recipient-local send strategies as a universal instant. Existing metadata with the earlier ambiguous semantics remains unverified: this change does not rewrite production metadata or initiate collection. Missing metadata/timestamps cause one request for a name or send date; a supplied reply updates/retries the pending request, or explicitly reports remaining unavailable evidence without repeating that question. Supplied dates are labeled as user evidence, not actual provider timestamps.

“Since it was sent” and “since sending” select the same date-basis intent. The actual instant is converted into the selected campaign’s reporting timezone and bounded by the earlier of the submission day and supported collected reporting cutoff. For a send at `2026-09-20T23:30:00Z`, London start date is `2026-09-21`; with September-only collected reports the cutoff is `2026-09-30`. Provider performance arguments include those dates and `campaign_id`, `campaign_account`, `campaign_channel`; the single-account persisted binding validates account/channel before querying, and SQL filters `report_kind='campaign' AND entity_id=@campaign_id`. Named requests use parameterized exact name/ID matching.

The existing attribution binding supports calendar-month message report windows, not purchase-occurrence calendar dates or timestamp slicing. The query expands dates to supported whole windows and the answer displays actual evidence dates and expressly declines a precise since-send count. The evidence carries the actual send timestamp, date basis, reporting granularity, coverage, retrieval freshness and source definitions. Counts remain source-native attributed conversion events. Reviewed Placed Order provenance supports the wording “Klaviyo attributed X purchases to this campaign”; other metrics remain conversion events. Neither count establishes distinct orders or purchasing recipients. Rows retain their conversion metric, currency and attribution population; currencies are never summed or converted. Attribution settings at retrieval do not establish historical applicability, and recent attribution can be provisional.

Attribution and coverage reads settle independently. Successful rows survive a coverage failure; successful coverage survives an attribution failure. A Shopify referrer comparison failure preserves Klaviyo attribution. A report failure preserves already resolved send evidence and pending state for retry. Failure is never converted to zero activity. The presentation shows campaign identity, date basis, timezone, freshness, attribution wording and month-granularity limitations before supporting details.

`test/oracle-campaign-continuity.test.js` exercises the exact production two-turn exchange through shared dispatch, the direct governed agent entrypoint, authenticated interactive HTTP and durable workers/polling. It covers fresh contexts and prior product-export/device-conversion contexts; latest email, since sending, named campaigns, explicit date refinements, account/channel ambiguity, duplicate names, missing metadata/timestamps, supplied ISO/named send dates, future sends, monthly evidence, multiple currencies, conversion definitions, identity disagreement and partial component failures. Assertions inspect actual provider arguments and production dependency BigQuery query parameters and predicates. Existing product report population filters, configuration identity checks, workbook exports and continuity tests remain in the regression suite.

No production queries, source collection, backfills, source mutations or deployment are performed. Verification uses local fixtures with the production dependency factory, router, worker and renderer. Production metadata freshness, provider access and deployment acceptance remain unverified.
