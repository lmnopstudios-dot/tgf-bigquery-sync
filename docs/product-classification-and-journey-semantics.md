# Governed product classification and acquisition journeys

## Catalogue evidence and population

### SQL repair

The production failure was generated by `loadCatalogueEvidence` in `product-classifications/sync.js`. It emitted a STRUCT field such as `TO_JSON_STRING(product_type) product_type`; BigQuery's STRUCT expression list requires `AS` before the alias, so the parser reached the second `product_type` while expecting `)` or `,`. `metadataStructSql` now emits an expression of the form `TO_JSON_STRING(field) AS field` with BigQuery identifier quoting (and comma-separated equivalents), and returns an empty JSON object for an empty field list. SQL-shape tests cover zero, one, and multiple fields.

### Shopify catalogue and governance

`sync:shopify-catalogue` uses the existing Shopify client-credentials integration (or an explicit access token), cursor-paginates products, collections, and every collection's products, and persists stable numeric Shopify IDs. The normalized `shopify_catalogue.products`, `shopify_catalogue.collections`, and `shopify_catalogue.product_collections` tables retain product type, vendor, tags, status/timestamps, collection display metadata, and the product-to-collection relationship. Product and collection MERGEs are idempotent; each complete collection snapshot replaces stale membership edges. Archived products remain visible through their source status rather than being mistaken for deletion.

The sync creates one `catalogue_synced_at` ingestion timestamp before fetching the catalogue and materializes it on every product, collection, and membership row; Shopify `created_at` and `updated_at` remain independent nullable source timestamps. All collection membership pages are fetched before any BigQuery write. Consequently, an incomplete fetch performs no upserts or stale-membership deletion. Persistence runs product and collection upserts before the authoritative membership MERGE, so a later persistence failure can leave those non-destructive upserts in place, but deletion only occurs in the final, statement-atomic membership MERGE after a complete snapshot has been fetched and locally validated.

Collections acquire meaning only through append-auditable `commerce.collection_classifications`. The Oracle API exposes authenticated/CSRF-protected list, decide, and revoke routes under `/api/oracle/collection-classifications`. A reviewer may set `collection_group=collaboration` or `collection_group=other` and separately provide `collaboration_name`; no collection title, handle, product title, tag, or model knowledge makes that decision automatically.

Shopify `product_type` is mapped only when its exact normalized value is in the governed vocabulary. The production catalogue validator returns bounded aggregate value/counts so aliases can be added only after business review. Current direct examples need no alias: `Ring` becomes `ring` and `Necklace` becomes `necklace`. Vendor and tags are retained for audit but are not category or collaboration classifiers.

### Historical taxonomy discovery

`validate:catalogue-production` audits all Woo WW/USD and Square tables and columns whose names indicate product, category, taxonomy, tag, attribute, item, or catalogue evidence; it is not limited to order lines. Persisted category fields are consumed only as exact structured category values. Explicit governed Woo collaboration taxonomy may be supplied as `taxonomy_collaborations`; title reconstruction and fuzzy matching are prohibited. If production discovery finds no relationship, the exact missing input is a Woo/Metorik product export or API response containing store, stable product ID, category ID/name/slug, and product/category membership. Square similarly remains unknown unless category evidence exists.

### Deployment order

1. Deploy the application.
2. Run `npm run sync:shopify-catalogue`.
3. Run `npm run validate:catalogue-production` and review its bounded `product_type`, collection, Woo taxonomy, and Square evidence.
4. Use the Oracle collection-classification endpoints to govern every relevant Shopify collection (collaboration or other) and provide collaboration names.
5. Ingest an authoritative Woo taxonomy export/API source if discovery reports the documented gap.
6. Run `npm run sync:product-classifications`.
7. Run `npm run validate:customer-journey-production`.

`sync:product-classifications` first inspects `INFORMATION_SCHEMA.COLUMNS` in the persisted Shopify, Woo WW, Woo USD, and Square datasets. It reports and reads only actually present catalogue tables/fields from the bounded allow-list: product type, tags, collections, categories, attributes, vendor, and item/catalogue metadata. A missing field is not assumed and a product with no usable evidence remains unknown.

The governed classification dimensions are `product_group`, `collaboration_name`, broad `product_category`, and specific source `product_type`; Shopify collection membership remains independently queryable. Category values are accepted only when the platform's designated structured category field exactly normalizes to one of ring, pendant, necklace, bracelet, chain, earrings, clothing, accessory, gift voucher, or other. Titles are never inputs. Collaboration membership and names require an active governed Shopify collection decision or explicit authoritative Woo taxonomy; arbitrary tags and category text never establish them. Absence is unknown, not core or non-collaboration.

Human-approved active records take precedence over authoritative catalogue records, which take precedence over canonical propagation. Propagation accepts only active deterministic or explicit governed mappings. Suggested, rejected, revoked, and conflicted edges are ignored. Origin reference and evidence are retained. Contradictory active values at a subject/type become `conflict`, remain diagnosable, and are excluded from journey SQL, without disabling unrelated classifications.

The sync creates the table if absent and deterministically MERGEs stable IDs. Its aggregate result includes inserted, updated, unchanged, conflicts, skipped unknown, and breakdowns by source, classification type, and provenance. It does not alter source catalogue data. Human product records retain the existing append/supersession-ready contract; collection decisions use the focused Oracle governance surface described above.

## First-order semantics

Acquisition journeys default to `first_observed_ever`: qualifying orders are loaded through `observation_end`, sequenced across all available governed history, and only then filtered by `cohort_entry_start` / `cohort_entry_end`. `first_observed_in_period` is an explicit alternative that applies the lower entry bound before sequencing. Cancellation, status, migration, refund, and identity qualification are unchanged.

“Ever” means available governed history for a source-qualified identity. It is not proof of a customer's first-ever TGF transaction. No Woo-to-Shopify identity is asserted, and anonymous historical Square activity remains unavailable. Source coverage floors are therefore the earliest persisted qualifying source dates; the production validator reports the material period-relative difference rather than inventing earlier history.

## Production validation

The read-only validator audits persisted metadata fields, per-source product and line/sales classification coverage, collaboration-known coverage, names/categories, provenance, conflicts and unknowns. It also reports customers whose global first order predates the entry period, cases where in-period semantics would differ, and the eligible acquisition cohort. Collaboration acceptance remains fail-closed until active collaboration records exist.

## Governed Shopify dimensions and collection review

Shopify `product_type` is preserved as its own first-class dimension and mapped to a broad `product_category` only by the centralized exact-value contract in `product-classifications/shopify-product-type-mapping.js`. Blank and new values remain category-unknown and appear in validation. Product titles are never classification inputs. Collection membership is independent of both dimensions and remains queryable even while its optional business classification is unresolved.

Oracle → Product Classifications → Collections is the focused human review surface. It lists every current collection, defaults to product-count order, supports search/status filtering, shows a bounded current-product preview and immutable decision history, and requires explicit confirmation of Collaboration plus an editable collaboration name or Other/non-collaboration. Changing a decision supersedes rather than destroys its predecessor; revocation retains history. No title-based or bulk automatic classification exists.

Current catalogue membership is authoritative for collaboration derivation. Multiple governed collections with one collaboration name deduplicate; different names conflict on `collaboration_name` while generic `product_group=collaboration` remains valid. Sync supersedes active derived rows no longer supported by current membership. Woo `tags_json` remains explicitly non-authoritative for taxonomy. Square `categories.category_data_name`, `item_data_category_id`, and `item_data_product_type` are retained as evidence for a later governed Square task and are not expanded here.
