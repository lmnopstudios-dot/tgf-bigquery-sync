## Shared contract and control records

`oracle/freshness.js` defines cadence, source lag, overlap, dependent tools, requested versus actual coverage, source success time versus query time, provisional periods, overdue status, and source-specific unavailable/stale text. Dependency entries are based on actual query/report data use, not registry-name existence: `get_klaviyo_email_performance` reads Klaviyo only; `compare_klaviyo_email_with_shopify_referrer` additionally reads Shopify conversion/referrer evidence. A query executed today is never evidence of collection today.

Daily inspections return `missing_dates`, rather than only a count. Missing rows are not automatically confirmed source-collection gaps: a failed or unexecuted collector, an intentionally historical table, and an upstream absence require different conclusions. Likewise, an observed zero row/value is not a missing date.

## GA4 instrumentation boundary

Stuart reports that ecommerce tracking was not configured properly when Shopify launched and was fixed sometime in September 2026. The exact correction date and affected events remain unknown. The audit therefore marks every ecommerce table boundary `instrumentation_boundary_unverified` and reports table-specific ranges and missing dates. Before making a historical ecommerce claim, inspect daily `conversion_coverage` statuses/reasons, `conversion_device`, `conversion_breakdown`, and `ecommerce_funnel` together to identify the first sustained reportable evidence; record conflicting or sparse periods as uncertain rather than choosing a date.

This separates two failure modes: (1) collection omitted events which GA4 did record and may still expose through its API; and (2) ecommerce events were never/incompletely instrumented and cannot be recovered by a backfill. Sessions/acquisition remain separately usable when their table-specific coverage is sound. For Shopify-period sales and conversion reporting, prefer Shopify-native evidence with its own definitions. Do not splice Shopify values into GA4 measures, and do not translate absent GA4 ecommerce events into zero Shopify sales. Oracle answers and reports must retain this historical limitation while ongoing GA4 collection remains enabled.

`oracle_ops.collector_runs` records every started, succeeded, or failed invocation. `oracle_ops.collector_state` advances only after the source collector has completed its staged/transactional promotion. The runner uses a BigQuery transaction assertion to prevent concurrent live leases, records failures, and records zero-byte/zero-row-success output separately from missing runs. Stale `running` records older than six hours no longer block recovery, but remain as failure evidence for operators to classify.

## Deployment and bounded catch-up

1. In Render Blueprint, review and apply `render.yaml`. Add the secret environment variables: `GOOGLE_PROJECT_ID`, `GOOGLE_SERVICE_ACCOUNT_JSON`, Shopify credentials, `GA4_PROPERTY_ID`, Klaviyo credentials/config, and Search Console access through the Google service account. The shared list in YAML intentionally marks secrets `sync: false`.
2. Run `npm run audit:freshness` and retain its JSON. It inspects table min/max coverage and the last five persisted executions. For retired Woo it reads historical order coverage only and emits `retired_no_schedule`; it does not create a run, watermark, freshness alert, or catch-up job. Inspection failures are reported, not converted into zero activity.
3. Before enabling a cron whose source maximum is missing, run an evidence-based bounded catch-up. Never initialize its state at now:
   - Finance: `npm run refresh:shopify-finance -- --mode collect --start <last-proven-historical-end-ISO> --end <now-ISO>` (split into bounded windows if page limits require it), then `--mode scheduled`.
   - GA4 sessions/acquisition: after retaining the audit JSON and confirming the reported one-day gap, the exact seven-day-overlap command from the 2026-09-24 current-table endpoint is `npm run sync:ga4 -- --start 2026-09-18 --end 2026-10-01`. This keeps ongoing collection available, but does not promise recovery of unrecorded ecommerce events. Do **not** recommend the old `2025-11-12–2026-10-01` range unless production owners verify that the short conversion tables are intended current datasets and event-level evidence shows GA4 recorded recoverable events.
   - Shopify conversion: `npm run backfill:shopify-conversion -- --mode repair --start <day-after-last-covered-day> --end <yesterday> --chunk-days 7 --max-chunks 4 --max-sources 40 --timezone <IANA-zone>`; follow its emitted resume command.
   - Search Console: invoke `npm run sync:search-console -- --start <overlap-start> --end <today-minus-3-days>` in ranges no larger than 31 days.
   - Geography and catalogue: `npm run sync:shopify-shipping-geography` and `npm run sync:shopify-catalogue`; both paginate bounded API connections and promote idempotently.
   - Klaviyo: `npm run schedule:klaviyo` deliberately refreshes the previous and current London months. Use its bounded backfill/resume commands only for a proven older gap.
4. Scheduler verification (no activation is performed by this correction): inspect the Render Blueprint and environment, manually trigger only an approved active-source cron, retain its Render execution ID/log, then run `npm run audit:freshness` again. Require a new `oracle_ops.collector_runs` row with `status='succeeded'`, non-null `finished_at`, a plausible table-specific watermark, and the expected overlap coverage. Require `verified_scheduled_execution=true` only after a scheduled-mode run, not merely a manual success or snapshot timestamp. A deployed definition alone is not active automation.
