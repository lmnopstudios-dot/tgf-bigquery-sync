# Entity-relative campaign analysis

The production question “How did the last 3 Klaviyo campaigns go?” bypassed the merged single-campaign mechanism: `campaignContextPatch` recognised a singular latest/named campaign but not a counted selection. The generic Klaviyo route then marked calendar dates as required. Even the recognised single latest campaign asked for a reporting range unless the user explicitly supplied “since sent”. PR #303 already fixed campaign identity, send metadata semantics, clarification continuity and monthly attribution; this change extends that mechanism rather than recreating it. Merged PRs #321 and #322 remain the authority for shared operations and instruction/document boundaries.

The route is message intent → validated shared analytical context → independent entity selection → required reporting scope → governed Klaviyo provider → scoped evidence validation → shared presentation and delivery. The new entity-selection helper parses latest/previous/count rules and orders actual sends. The shared `campaign_request` and analytical plan separately retain entity type/source, count, ordering, offset, account/channel, selected campaign IDs/native send dates, reporting windows, metric requests and comparison intent. Explicit dates remain separate from selection; they override default send-relative reporting. Count-based selections resolve entities before any reporting-date requirement. Analysis is bounded to 1–10 primary campaigns, with at most one preceding comparison group.

The selection excludes drafts, unsent scheduled campaigns, flows and future sends. Campaign identity `(account, channel, entity_id)` collapses metadata snapshots/message variants; source message IDs do not become additional campaigns. Conflicting send metadata, missing verified timestamps, a tie at the selection boundary or an incomplete listing prevents a claimed latest-N selection and asks for campaign names/identifiers. Multiple account/channel populations produce identifiable options. The production factory establishes only the configured `production` account and email channel; it does not invent SMS or another account. Fewer available campaigns remain visible with the gap disclosed.

Each campaign has its own reporting window, from its actual send date in the provider reporting timezone to the earlier of submission day and collected reporting cutoff. The persisted provider supports only exact calendar-month reports: its SQL excludes overlapping/rolling windows and keeps the latest snapshot of each campaign/message/report-window/conversion-metric key before summing native values. No new provider query, collector or report granularity is invented. A September send may therefore retrieve a September calendar-month report; this is explicitly not an exact post-send or purchase-occurrence slice. Sends beyond the supported reporting cutoff stay in the selection with unavailable attribution while older campaigns remain usable. Currencies/conversion-metric populations remain separate, including within a campaign table cell. Different campaign ages and provisional newest attribution remain visible; equal-age comparisons are unavailable from these monthly reports.

The default table shows one campaign per row: sent, delivered, native unique click rate, attributed purchases/conversions and credited revenue, with explicit unavailable values. Multiple currencies/metric populations are separately labeled, never added. Reviewed Placed Order provenance supports purchase-event wording, not distinct orders. Credited revenue does not establish incremental sales; native rate denominators, open-rate limitations, attribution settings and their unverified historical applicability are retained in Show details.

Previous-N and comparison requests retain the original cutoff/account/channel and offset the send-ordered population. “Best” discloses credited revenue as its default ranking metric, separately by native population, with attribution-age limits. Email narrowing, clicks, explicit dates, retry/refresh and export retain compatible identities and metric requests. Best/click/export can reuse validated scoped evidence; retry/refresh retrieves the same selected IDs/windows. Subject switches clear incompatible campaign state; existing document/instruction and knowledge-save gates run before campaign interpretation.

Delivery uses the existing shared result contract. Context/plan/evidence validation checks campaign identities, ordering, native dates, per-campaign windows, sections, row populations and requested metrics before presentation, recovery or export. XLSX bytes use the existing owned durable export store; download validates hash, workbook cells and analytical scope. Poll recovery can restore a saved campaign artifact after a failed final job write without calling providers again. Normal application job/artifact writes are confined to test fixtures here.

## Related capability audit

- Reviewed historical-event comparison already selects confirmed past events and derives windows from effective dates, including the reviewed Black Friday phase relationships. Its scope/required-date behavior is preserved.
- Product selection identifies products but does not establish the calendar period for their sales history; its reporting-date requirement remains appropriate. Current inventory is a snapshot capability, not a last-N event analysis.
- Meta campaign performance is a requested-period aggregate; its governed analytical contract does not establish latest sent-campaign ordering. Instagram/TikTok social reports likewise do not register this sent-campaign selection contract. No entity-relative date bypass is added to them.
- Sales, conversion, shipping, customer and search capabilities require governed calendar populations; no entity-native event scope is fabricated for those providers.

## Verification and live limits

`test/oracle-entity-relative-campaigns.test.js` checks exact/paraphrased questions through shared context, dispatcher, direct agent, production dependency factories and authenticated interactive/durable HTTP. It asserts ordered campaign IDs, provider SQL parameters, per-campaign reporting windows, actual rendered Markdown table structure, account/channel clarification, message variants, missing/conflicting/tied metadata, monthly-only evidence, cutoff limits, partial failures, missing metrics/currencies, previous groups, ranking, clicks, subject/document boundaries, owned workbook bytes, browser-recovery endpoints, persisted artifact recovery and same-ID replay. Existing campaign, shared-plan and clarification regressions remain in place; obsolete expectations of the generic campaign date question now assert automatic scope instead.

The final focused campaign/shared-plan/clarification run passed 127/127 tests. Tool validation passed 46 strict schemas across 61 registered tools, and `git diff --check` passed. Full-suite results are recorded in the PR. Fixture tests verify the production code paths; they do not establish live production metadata freshness, credentials, provider access, deployed behavior or browser acceptance.

## Bounded read-only diagnostic

`node diagnostics/oracle-campaign-selection.js` prints the bounds and required configuration without remote reads. With the intended project/credentials configured, `node diagnostics/oracle-campaign-selection.js --execute-read-only` permits at most seven SELECT queries (one metadata/cutoff plus three attribution/coverage pairs), at most 1 GB billed per query, a 15-second per-call deadline and a 60-second total deadline. Output contains selected campaign IDs, reporting windows, row counts, coverage and bounded stage/count diagnostics. It excludes prompts, credentials, campaign content, recipients, customer data and raw exceptions. A deadline bounds client waiting, not server-side cancellation of an already submitted SELECT job.

Remaining live checks: run the bounded probe against the intended production project; verify actual send metadata and campaign/message identities, collected cutoff/freshness, native metric definitions and attribution settings; then verify the exact question and follow-ups in the deployed authenticated UI with polling/recovery and owned downloads. No collection, backfill, source/knowledge mutation, schedule change, deployment or merge is included.
